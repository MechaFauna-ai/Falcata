How the search works

A population of code candidates, developed through repeated tests.
  1. 01 / INHERIT

    Start from a parent

    A candidate builds on an existing implementation. Separate branches can explore different bottlenecks without discarding useful earlier work.

  2. 02 / VARY

    Propose a change

    An AI worker changes the code. In the library searches, it records an observation, a hypothesis, and a test that could prove the idea wrong.

  3. 03 / EVALUATE

    Measure and challenge it

    The operator benchmarks the candidate and checks correctness. Eligible library changes also receive independent code review; model checks and timing must pass before review.

  4. 04 / SELECT & REPEAT

    Continue useful branches

    Useful candidates become starting points. Changes can be combined, or an idea can be reused on another branch. Failed and inconclusive attempts stay in the archive.

Repeat from a useful parent ↺ The search is a branching history, rather than a single uninterrupted march toward faster code.

Two search scales, different evidence

Early searches used OpenEvolve to sample a parent and inspiration programs, then evolved isolated kernels against captured launches and correctness layouts. Later searches evolved branches of the whole library, recording explicit hypotheses, model checks and review. Each campaign keeps its own baseline and measurement protocol. Missing replay ancestry remains missing; evaluation order does not invent parent edges.

READING THE LINEAGE

Code inheritance,
idea reuse, and evidence.

A parent edge records the implementation a candidate started from. A combined parent edge identifies a second branch offered to the worker; it does not prove that every change was incorporated. Violet edges track hypothesis continuation or idea reuse; they do not imply that the same code was inherited. Green integration edges connect documented changes to release code.

The speed filter uses a point estimate against the measurement baseline. Original labels such as “improved” compare a candidate with its parent. It can beat the baseline and still regress from its parent, or pass replay checks without entering a release. “Accepted” means eligible in that search; integration is recorded separately.

Kernel replays, construction timings, short probes and full training measure different things. Their ratios are never multiplied into a release speedup here. Reused results are cached evidence, not fresh measurements. Select a record to see the protocol, checks and original hypothesis; select its connections to follow the next branch.
